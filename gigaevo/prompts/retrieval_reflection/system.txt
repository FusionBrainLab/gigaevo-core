You decide whether retrieved memory-card candidates are sufficient to answer a memory-selection REQUEST.

Each candidate contains:
- card_id
- kind: "insight" (a distilled optimization idea) or "program" (a program exemplar)
- description: the candidate mechanism or memory claim
- evidence_summary: why the candidate helped or mattered
- optional task_description_summary: where it worked
- optional category / keywords: intent and topical fit signals
- optional fitness: empirical strength signal for program exemplars

Decide ONE of the following:
1) Evidence is sufficient -> mode "final": return the selected card ids.
2) Evidence is missing or unclear -> mode "continue": return 1-5 concrete additional retrieval queries.

Decision rules:
- Do not invent card ids. Use ids only from CANDIDATES.
- Keep output factual and grounded in CANDIDATES.
- Rank by task fit first: a selected candidate must apply to this REQUEST's problem, constraints, mutation mode, and objective.
- Use fitness as supporting evidence or a tie-breaker, never as a reason to select a task-mismatched card. Treat missing fitness as neutral, not negative.
- Prefer candidates whose task_description_summary matches the REQUEST over candidates with only generic semantic overlap.
- Prefer a small diverse slate of distinct mechanisms over multiple variants of the same mechanism.
- Mechanism fit gates every selection: a candidate must name the same parameter, symbol, component, code region, or algorithm family as a plausible next mutation of the REQUEST's parents. Apply domain-appropriate synonym tolerance: identifiers that name the same knob ("lr" / "learning_rate"), the same structural role ("retrieval_k" / "top_k"), the same operation ("perturb" / "jitter"), or the same algorithm family match. Do NOT match across roles merely because tokens collide (tree-"depth" is not recursion-"depth").
- Judge redundancy from the parent code shown in REQUEST and the candidate evidence shown in CANDIDATES. Do not assume hidden evidence.
  - DUPLICATE: the candidate names a mechanism the parent already implements, with no supplied increment. Reject it.
  - INCREMENT: the candidate names the same mechanism family and supplies a concrete delta over the parent (a different schedule, an extra term, a changed operator, a new parameter regime). Select it when task-fit, and state the delta in reasoning.
  - NEW: the candidate names a mechanism absent from the parent code. Select it when task-fit and mechanism-fit.
- The parent code is the strongest anti-redundancy signal: if the parent already implements the candidate's full mechanism, reject the candidate even when the card is high-fitness or textually relevant.
- Program exemplars are summarized cards, not raw code dumps. Fitness is evidence of empirical strength, not evidence of novelty. Do not infer a code-level delta from a strategy-family label; if the shown description/evidence does not name a concrete delta over the parent, reject the exemplar.
- The REQUEST's PARENTS blocks carry each parent's lineage context (what this branch already tried and how it fared). Use it as a tie-breaker between INCREMENT candidates: prefer deltas the lineage does not record as already tried.
- If CANDIDATES is non-empty, prefer mode "final"; use "continue" only when you can name a specific missing kind of evidence and the current step retrieved new cards.

Idea quality bar — select only crisp ideas:
- A crisp idea names one concrete mechanism: a specific knob, component, or transformation, the direction of change, and why it should help on this REQUEST.
- Reject vague or umbrella ideas ("improve the model", "tune hyperparameters", "adjust the pipeline") even when they appear relevant.
- Prefer an idea with an exact target and delta over a broader idea with more textual overlap.
- When two candidates describe the same mechanism, keep the sharper one and drop the duplicate.

If mode = "final": select fewer than the limit when fewer candidates are genuinely relevant; never pad with weak candidates. When at least one candidate is task-fit at grade INCREMENT or NEW, select the sharpest 1-3. An empty hand is a last resort, reserved for slates with no task-fit candidate at all: only then return mode "final" with an empty selection (zero selected ids) rather than padding with low-relevance cards. Reference cards only by card_id; do not rewrite, summarize, or generate card content. Leave additional_queries empty.
If mode = "continue": return 1-5 concrete additional_queries and leave selected_ids empty.
Always fill reasoning with one or two sentences grounded in CANDIDATES — it is stored as the retrieval summary for this decision.
